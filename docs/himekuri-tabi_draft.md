# 祭り×旅行カレンダー プロジェクトメモ

Nov 19, 2026 · @康平

## 概要

2〜3ヶ月先の旅行の日程と行き先を入れると、その期間・周辺でかぶる祭りやイベントが出てくるWebサービス。天神祭やラーメン祭りのような国内の祭りと、海外の主要な祭りを一つにまとめる。

- 位置づけ：個人開発。ゆるく続ける。ただし、作り込むところは作り込んでよい
- 主な利用者：旅行を計画している日本語ユーザー（国内旅行と海外旅行の両方）。最初の利用者は自分と友だち
- 名前：未定（デザイン案では `[サービス名]` と仮置き）

## なぜ作るのか

旅先を選ぶときに「どうせ行くなら、イベントにも参加できたら楽しい」と思っているから。祭りは旅行の目的そのものではなく、旅行をちょっと良くする「おまけ」。そのため大きな祭りだけでなく、ふらっと参加できる中規模のイベントにも価値がある。

## 使われる場面

- 友だちと行くことが多い。決まっているのは**1つだけ**（「11月に行く」のような時期か、「牧場に行く」のようなやりたいこと・場所）で、ほかは何も決まっていない状態から考え始める
  - **時期から**：「11月なら、ここでこんなイベントがある」と行き先の候補が出る（今のデザイン案にはない入口）
  - **場所から**：「その周辺だと、この週末にこんな祭りがある」と日程の候補が出る（デザイン案のカレンダー＋周辺50kmの絞り込み）
  - 日付と行き先がどちらも決まっていることもある（デザイン案の「日程で探す」）
- 候補はLINEのグループで出し合い、Discordで話して決める。サービス側は**URLを貼るだけで共有できる**ようにする（OGPのカード、検索条件をURLに持たせる）。アカウント、投票、グループ機能は作らない（仮）
- 海外：行ったことがなく、そもそも何も知らない。「トマト祭りがあるなら行ってみたいが、時期を知らない。たまたま時期が合ったら行きたい」。国内とは違い、**眺めて知る**ための場所にする

## ゴールと制約

ゴール：

1. 友だちとの旅行で実際に使って、行き先や日程を決められる（最初の成功の基準）
2. Webアプリのオーナーとして経験を積む。SEO、アクセス解析、広告、データ更新の運用を自分で回し、お金のかからない範囲で少しずつ拡大を目指す
3. 広告とアフィリエイトでゆるく稼ぐ仕組みを最初から持つ

お金の制約：

- 運用費は年5,000円程度まで（独自ドメイン代を含む）。MVPの間は実質0円（Cloudflareの無料枠＋`workers.dev`）
- 勉強代として数万円くらいまでなら使ってもよい（来年以降）
- LLMは使ってよい：この開発PCのローカルLLMか、月500円程度で済むクラウドのAPI（毎月使うと年5,000円の枠を超えるので、使い始めるときに枠を見直す）

ここから出てくる方針（仮）：

- 稼ぐ仕組み（1祭り1ページ、OGP、広告枠、宿のアフィリエイトリンク）は最初から作る。データは自分たちが旅行で使う地域から増やす
- インフラはCloudflareの無料枠（技術メモを参照）。MVPは `himekuri-tabi.idotworks-lab.workers.dev`。名前が固まったら.comを取り（年1,600円前後）、いつでも切り替えられるように作っておく。Search Consoleは.comに切り替えてから登録する
- データ収集：MVPはClaude Codeで下書きを作って人が確認する。自動化するときは、ローカルLLMか安いクラウドのAPIを使う

## 決定事項

| 項目 | 決めたこと |
| --- | --- |
| 提供形態 | スマホ前提のWeb。ネイティブアプリは後回し。検索ページ＋1祭り1ページ（SEOの流入口、兼、友だちに貼るリンク）＋iCalの購読フィード |
| 対象範囲 | 国内と国外で分けてまとめる。全部は扱わず、動員数の推計で絞る。MVPは国内の京都・大阪・沖縄・北海道から。海外はその次の段階で、人の手で選んだ有名な祭り20〜30件を足す（仮） |
| 国内と海外のUI | 同じサイト・同じデザインで、入口と見せ方だけ変える（仮）。国内は「決まっている1つから探す」、海外は写真つきカードを月ごとに眺める。1祭りのページ、月の一覧、iCal、部品は共通 |
| 収益化 | 広告で細々と。将来的に企業経由のPR。宿へのアフィリエイトリンクは最初から1個だけ置く |
| 予約機能 | 後回し。カレンダーがメインで、航空券・バス・宿は付け足せればいい。自前では売らず、アフィリエイトのディープリンクで飛ばす |
| トップ画面 | 「いつ」「どこ」の両方を空でもよい1つのフォームにする（案A）。いつだけ→行き先の候補、どこだけ→その周辺のカレンダー、両方→かぶる祭りと日程ずらしの提案。旧案の2タブ（「日程と行き先で探す」「カレンダーから探す」）から変更 |
| URLの形 | 探し方に関係なく、入れた条件だけで作る（例：`/?when=2026-11&where=kyoto`）。共有リンクやSEOを壊さずに、入口の画面を後から作り替えられるようにする。検索は1つの部品（`search({when?, where?})`）にまとめ、画面はその上に乗せる |

## プロダクト設計

機能：

1. **日程と行き先で探す（本体）**：行き先＋出発日＋帰着日で、かぶる祭りを一覧と地図で出す。規模（1万人〜／10万人〜／100万人〜）で絞れて、周辺50kmも含められる（京都旅行なら大阪の天神祭も出す）
2. **日程ずらしの提案**：「3日前にずらすと祇園祭 前祭の山鉾巡行も見られる」のように出す。一番の差別化ポイント
3. **混雑の警告**：大きな祭りの日に「宿が埋まりやすい日」と出す。避けたい人にも役立つ
4. **カレンダーから探す**：月のカレンダー。フィルターなしなら全国から人気順に1日2件＋「+N件」。都道府県を選ぶとその県だけになる。日付を押すとその日の一覧と「近くの宿を見る」
5. **カレンダー購読（iCal）**：「関西 × 10万人〜」のような条件をGoogle／Appleカレンダーに追加。日程が確定・変更されたら自動で反映
6. **宿へのリンク**：祭りの日付と場所を載せたアフィリエイトリンク

イベントのデータモデル（最初から入れておく項目）：

| 項目 | 中身 |
| --- | --- |
| 名前・都道府県・国 | 国内か国外かの区分も |
| 緯度経度 | 半径での検索用 |
| 開始日・終了日 | 複数日や、日程が飛び飛びの行事に対応 |
| 日程の状態 | 確定（公式発表か毎年固定日）か、推定（「7月最終土曜」などの例年ルールや旧暦から計算）か |
| 日程のルール | 推定に使う例年ルールそのもの |
| 動員数の推計 | 出典と推計であることを一緒に持つ |
| ジャンル | 祭り／花火／グルメなど |
| 最寄りの都市・空港 | 宿や便へのディープリンク用 |
| 公式サイトのURL | 確認と差分チェックの元 |

## MVPの範囲

基準：友だちとの旅行で使えるか。予算内で作れて、運用の経験につながるか。

MVPに入れる：

| 機能 | 理由 |
| --- | --- |
| 時期から探す（月を入れると行き先の候補が出る） | 一番よくある場面（「11月だけ決まっている」）に対応する |
| 場所から探す（カレンダー＋周辺50km） | 「牧場に行く」の場面に対応する。デザイン案のカレンダーに絞り込みを足すだけ |
| 日程と行き先で探す | デザイン案のとおり |
| 日程ずらしの提案 | 前後数日を調べるだけで作れる。一番の差別化ポイント |
| 混雑の警告（簡易版） | 動員の多い祭りの日に「宿が埋まりやすい日」と出す。宿のデータは使わず、ルールだけで判定する |
| 規模の絞り込み | デザイン案にあり、作るのも簡単 |
| 1祭り1ページ＋共有用のURLとOGPのカード | LINEとDiscordに貼るため。SEOの入口も兼ねる。OGP画像は最初は共通の1枚 |
| 確定か推定かの印、出典のリンク | データの質で勝つという方針の中心 |
| 宿のリンク1個 | 楽天トラベルなどのアフィリエイトは無料で登録できる |
| アクセス解析とSearch Console | 無料で、運用の経験を積む第一歩 |

後回しにする：

| 機能 | いつ足すか、なぜ後回しか |
| --- | --- |
| 海外の祭り | 次の段階。データの形だけは最初から対応させる |
| iCalの購読 | 海外を足すときに一緒に作る（「時期が合ったら行く」で一番効くため） |
| 地図の表示 | 一覧と距離の表示で足りる。Leaflet＋OpenStreetMapで0円で後から足せる |
| 広告枠 | AdSenseの審査には独自ドメインとある程度のページ数が要る。データが育ってから入れる |
| 祭りごとに生成するOGP画像 | Workersで後から作る |
| 日程の差分チェックの自動化 | 来年の勉強代の候補 |
| PC専用のレイアウト | スマホ版を広げたもので済ませる |

## 競合と隙

隙はあるが狭い。「旅行の日程×行き先でかぶるイベントを出す」機能は海外勢が始めている。空いているのは、日本語で、日本の伝統的な祭りと海外の祭りを、確定前の日程も含めて扱うところ。

| 種類 | 主なプレイヤー | メモ |
| --- | --- | --- |
| AI旅行プランナー | [Mindtrip](https://www.chriscruises.com/?p=105535) | 一番の直接競合。2025年11月にイベント機能を追加。数十万件を集約、対象地域は非公開 |
| 都市×日付のイベント検索 | [Krugo](https://apps.apple.com/ca/app/krugo/id1393726426)、Eventseeker、Eventbrite | コンサートやスポーツなどチケット系が中心。日本の祭りはほぼ扱っていない |
| B2Bのイベントデータ | [PredictHQ](https://www.predicthq.com/major-events/countries/japan) | 日本の動員数推計をすでに提供（例：西宮の十日えびすを100万人）。ホテルの価格調整向け。競合であり、データ源の候補でもある |
| 国内のおでかけメディア | ウォーカープラス、オマツリジャパン、じゃらん | ウォーカープラスは[月間2億PV超（2023年7月）](https://mediaguide.kadokawa.co.jp/archives/018/202406/ウォーカープラス%20メディアガイド_202406.pdf)でSEOが強い。どれも日程を入れて検索できる作りではない |
| 国内の旅行計画アプリ | NAVITIME Travel、NEWT、Tabiji | 旅程と予約の管理が中心。イベントを重ねる機能は見当たらなかった |

狙う隙：

- 日本語×日本の伝統的な祭り×確定前の日程（旧暦や例年ルールからの推定と、確定時の通知）
- 日程ずらしの提案（調べた範囲ではどこもやっていない）
- 海外の祭りを日本語で（日本から海外に行く人向け）

## 技術メモ

- **インフラ（確定、MVPは実質0円）**：Cloudflare Workers（静的アセット）。GitHubのリポジトリとつなぎ、mainへのプッシュで自動公開する。検索のAPIは持たず、祭りのデータをJSONで配ってブラウザの中で検索する。アクセス解析（Cloudflare Web Analytics）は最初から入れる。独自ドメイン（.com）は名前が固まったらCloudflare Registrarで取る（原価、年1,600円前後）。サイトのURLは設定の1か所にだけ書き、いつでも切り替えられるようにする。Search Consoleは.comに切り替えてから登録する
  - 選んだ理由：広告やアフィリエイトのサイトでも規約上問題がない（GitHub Pagesは商用目的がグレー、Vercelの無料プランは商用利用不可）。静的配信の転送量は実質無制限。OGP画像の生成、iCalのフィード、日程の差分チェックの定期実行（Workers、Cron Triggers）を、無料枠のまま後から足せる
  - Cloudflareのアカウント作成と、GitHubとの連携は本人が行う
  - 以前の案：S3＋CloudFrontの静的サイト＋Lambdaの検索API＋定期実行のLambda。月数百円程度の見込み（未検証）。少額でも課金が出るので見送り
- **データ収集**：公式サイトや観光協会のページから、日程と動員数を抽出。人は差分を確認するだけにする。MVPはClaude Codeで下書きを作る。自動化するときは、ローカルLLMか月500円程度のクラウドのAPIを使う。毎年の日程更新が一番の運用コストなので、ここの自動化が続くかどうかを決める
- **動員数**：ほぼ主催者発表で盛られがち、実人数か延べ人数かもバラバラ。「推計値」と明記する。PredictHQのAPI（無料トライアルあり、料金は未確認）も候補
- **予約系アグリゲーターの仕組み（参考）**：
  - メタサーチ（Skyscanner、Google Flights、バス比較なび）は売らず、パートナーから受け取った運賃を表示して送客手数料を得る。[Google Flightsに公開APIはない](https://phptravels.com/ja/google-flights-api)
  - OTAの航空券は、GDS（Amadeus、Sabre、Travelport）、[NDC](https://www.travelvoice.jp/20181030-120264)（IATAの新しい流通規格で、航空会社と直接API接続）、コンソリデーターから仕入れる
  - 日本の高速バスは共通の予約システムにつなぐ。例：工房の「発車オ〜ライネット」は[OmioとAPI連携](https://voix.jp/?p=89920)
  - 実装の肝は、検索結果のキャッシュと予約直前の運賃の再確認、仕入れ元ごとの表現の正規化、予約後の取消・払い戻し
  - 自前で売るのは無理筋（旅行業登録やGDSの契約が必要）。アフィリエイトのディープリンクで十分

## リスク、未決事項、次のアクション

リスク（勝つための前提ではなく、経験を積むうえで向き合う課題として扱う）：

- 一番の敵は汎用のAIアシスタント。「7/15〜20に京都でかぶる祭りは？」はChatGPTやClaudeに聞けば済む。差別化は画面ではなく、日程の正確さ・動員数・確定時の通知というデータの質で取る。チャットが苦手なのは、日程が決まる前に2〜3ヶ月分を見渡して比べることと、確定か推定かを区別して示すこと
- ウォーカープラスなど大手とビッグワードのSEOで正面からぶつかるのは厳しい。ロングテールと、海外の祭り×日本語のすき間を狙う
- 広告だけだとお小遣い程度。宿のアフィリエイトが現実的な収益源
- 海外の祭りは動員数そのものが取れないものが多い
