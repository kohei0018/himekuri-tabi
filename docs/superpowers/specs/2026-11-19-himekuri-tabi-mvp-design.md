# himekuri-tabi MVP 設計書

2026-11-19 · 元になったメモ：`docs/himekuri-tabi_draft.md`（プロダクトの背景・競合・リスクはそちらを正とする）

## 1. 何を、なぜ作るか

旅行の「おまけ」になるイベントを見つけるためのスマホ向けWebサービス。

- サービス名（仮）：**ひめくり旅**。タイトル、ヘッダー、OGPに使う。表示名は後から変えてよい
- 公開URL：`himekuri-tabi.idotworks-lab.workers.dev`（Cloudflare Workers の名前＝リポジトリ名。アカウントのサブドメインは idotworks-lab）。共有リンクやSearch Consoleの登録に残るので、表示名が変わってもこちらは変えない

- 作る人（オーナー）は、旅先を選ぶときに「どうせ行くなら、イベントにも参加できたら楽しい」と思っている。イベントは旅行の目的ではなく、旅行をちょっと良くするもの。だから大きな祭りだけでなく、中規模のイベントにも価値がある
- よくある場面：友だちと旅行する。決まっているのは1つだけ（「3月〜5月のどこか」のような時期か、「牧場に行く」のような場所）で、ほかは何も決まっていない。候補はLINEのグループで出し合い、Discordで話して決める
- このサービスは、決まっている1つを入れると残り（行き先か日程）の候補をイベントつきで出し、そのURLをLINEに貼れば友だちに同じものが見える

### ゴール

1. **最初の成功の基準**：2027年3〜5月の友だちとの旅行で、実際に使って行き先や日程を決められる
2. Webアプリのオーナーとして運用の経験を積む（SEO、アクセス解析、データ更新、広告）
3. 広告とアフィリエイトでゆるく稼ぐ仕組みを最初から持つ

### やらないこと（MVPでは）

- 海外のイベント（次の段階。データの形だけは対応させる）
- iCalの購読、地図表示、広告枠、イベントごとのOGP画像、日程の差分チェックの自動化、PC専用レイアウト
- アカウント、投票、グループ機能（話し合いはLINEとDiscordに任せる）
- 出演者や対戦カードが主役のもの（ライブ、スポーツの試合）。コミケのような催し・コンベンションも「そのうち」
- 常設の施設・観光スポット
- 予約や決済。宿はアフィリエイトのリンクで外に送るだけ

### 失敗とみなすこと（動いていても）

- 日程が間違っていて、友だちとの旅行で信用できない。確定か推定かの区別がない
- 共有したリンクを友だちが開いて、貼った人と違うものが見える
- 運用費が予算（年5,000円程度）を超える

## 2. 制約

- **お金**：運用費は年5,000円程度まで。MVPの間は、実質0円（Cloudflareの無料枠＋`workers.dev`）
  - 独自ドメイン（.com、Cloudflare Registrarで年1,600円前後）は、名前が固まったら取る。**いつでも.comに切り替えられるように作っておく**（7章）
  - Cloudflareの有料プラン（Workers Paid、月5ドル）は予算を超えるので使わない
- **LLM**：使ってよい。この開発PCのローカルLLMか、月500円程度で済むクラウドのAPI。MVPのデータは、Claude Codeで下書きを作る。APIは、データ集めを自動化するときに使う
  - 月500円（年6,000円）を毎月使うと、ドメイン代と合わせて年5,000円を超える。APIを使い始めるときに、予算の枠を見直す
- **インフラ**：Cloudflare Workers（静的アセット）。GitHubの `kohei0018/himekuri-tabi` とつなぎ、mainへのプッシュで自動公開。アカウント作成と連携はオーナーが行う
- **リポジトリ**：ローカルの `himekuri` フォルダがそのまま `kohei0018/himekuri-tabi`（`origin` 登録済み、SSHのエイリアス `github-claude-dev`、まだコミットなし）。メモは `docs/himekuri-tabi_draft.md`、デザイン案の保存版HTMLは `docs/design/` に置く【設計者の判断】
- **サーバー側の処理は持たない**。検索はブラウザの中で行う
- **データ収集**：Claude Codeで下書き（YAML）を作り、オーナーがPRの差分で確認する
- 言語は日本語のみ
- 温度感：ゆるく続ける。ただし、作り込むところは作り込んでよい

## 3. 作り方の検討

| 案 | 中身 | 判断 |
| --- | --- | --- |
| **A. Astro＋イベントごとのYAML（採用）** | 静的サイトを生成。1イベント1ページを最初からHTMLで作る。データはGitで1ファイルずつ管理し、ビルド時にスキーマで検査する | LINEやDiscordのカード（OGP）が出るには、ページが最初からHTMLである必要がある。Cloudflareで公式に対応している。データの修正がそのままPRの差分になり、「人は差分を確認するだけ」と一致する |
| B. 素のHTMLとJS＋自作のビルドスクリプト | 依存が最小 | ひな形、スキーマ検査、ページ生成を全部自作することになり、ページが増えると散らかる |
| C. Next.jsやSvelteKit | アプリ向けのフレームワーク | このMVPには重い。CloudflareでNext.jsを動かすにはアダプターが要る。アカウント機能を作らないので強みが活きない |

データベース（Cloudflare D1など）は、30〜50件には過剰で、PRでの差分確認もできなくなるので見送り。数千件になったら見直す。

オーナーが案Aを選んだ。言語はTypeScript、テストはVitest。

## 4. 画面と動き

見た目はデザイン案に合わせる：[祭りカレンダー トップページ案](https://claude.ai/artifact/R2RnNfJovArwXRgqUArk2H)（ローカルの保存版：`docs/design/祭りカレンダー トップページ案.html`）。スマホのトップ（390px幅）が基準。

- 色：紺 `#1E2766`（帯）、`#2B3A8C`（主ボタン・確定バッジ）、朱 `#D23F2A`（主操作・日付）、本文 `#1A1C2E`、補足 `#5A5E73`、背景 白
- 確定は塗りのバッジ（`#E8EBF8`／`#2B3A8C`）、推定は点線のバッジ（`#FFF1EC`／`#A8321F`、`1px dashed #E3866F`）
- フォント：本文 Noto Sans JP、見出し Zen Kaku Gothic New（Google Fonts）
- タッチの対象は44px以上。PCではスマホの列を中央に広げるだけでよい

### 4.1 トップ（`/`）：「いつ」「どこ」のフォーム

デザイン案の2つのタブ（「日程で探す」「カレンダーで探す」）は使わず、1つのフォームにする。

```
いつ  [ 2027年4月 ▼ ] または [出発日]〜[帰着日]   （空でもいい）
どこ  [ エリアを選ぶ ▼ ]                          （空でもいい）
規模  (1万人〜)(10万人〜)(100万人〜)
[ 探す ]
```

- **いつ**：「月」か「期間（出発日〜帰着日）」のどちらかで入れる。月の選択肢は、データのある月（MVPは2027年3〜5月）
- **どこ**：エリアの一覧から選ぶ（4.4）。自由入力はしない
- **規模**：動員数のあるイベントだけにかける。見頃と展示ものは絞り込みの対象外で、常に出す
- 入れたものに応じて結果が変わる：

| 入れたもの | 出すもの |
| --- | --- |
| いつだけ | **行き先の候補**：その月や期間に、イベントがあるエリアを並べる。各エリアに件数と主なイベント2〜3件。並び順は 4.5 |
| どこだけ | **そのエリアの周辺50kmのカレンダー**：データのある月を月ごとに。デザイン案のカレンダー（1日2件＋「+N件」、日付を押すとその日の一覧）をそのエリアに絞ったもの |
| 両方（期間） | **かぶるイベント**の一覧＋**日程ずらしの提案**＋**混雑の警告**。デザイン案のスマホ版の結果部分と同じ |
| 両方（月） | そのエリアのその月のカレンダー |
| どちらもない | フォームだけ。下に「これから」のイベント一覧（デザイン案の「これから3ヶ月」の国内側）を出す |

- 入力を変えたら、結果とURLを同時に更新する（ページ遷移なし）。URLを開いた人は同じ結果を見る
- 「同じ結果」の意味：**条件が同じなら、その時点のデータで同じ結果になる**こと。日程が推定から確定に変わるなど、データが更新されれば結果も変わってよい。貼った時点の結果を固定する仕組みは作らない【設計者の判断】

### 4.2 URLの形

探し方に関係なく、入れた条件だけで作る。入口の画面を後から作り替えても、共有したリンクが壊れないようにするため。

- `when`：`2027-04`（月）か `2027-04-01..2027-04-05`（期間）
- `where`：エリアのID（例：`kyoto`）
- `size`：`10000` / `100000` / `1000000`（省略時は `10000`）
- 例：`/?when=2027-04&where=sapporo`、`/?when=2027-04-01..2027-04-05&where=kyoto&size=100000`
- 不正な値は無視して、その項目は空として扱う

### 4.3 1イベント1ページ（`/events/<id>/`）

ビルド時に静的に生成する。LINEとDiscordに貼るリンクであり、SEOの入口でもある。

- 中身：名前、日程（確定か推定か平年値かのバッジ＋推定なら例年ルールの文）、場所（市区町村）、ジャンル、動員数（「推計値」と出典）、説明（2〜3文）、公式サイト、出典のリンク、近くの宿のリンク、「このイベントがある時期で探す」（`/?when=<開催月>&where=<最寄りエリア>` へのリンク）
- `<title>`、`description`、OGPのタグ（`og:title`、`og:description`、`og:url`、`og:image`）、`twitter:card` を入れる
- OGPの画像はサイト共通の1枚（1200×630）。イベントごとの画像は後回し
- 検索結果のURL（`/?…`）のOGPは、サイト共通のタイトル・説明・画像でよい

### 4.4 エリア

「どこ」の選択肢。各エリアは中心の緯度経度を持ち、周辺50km以内のイベントをそのエリアのものとして扱う（エリア同士が重なってもよい）。

MVPの初期エリア（実装者が増減してよい）：京都市、嵐山・嵯峨野、大阪市、USJ・ベイエリア、那覇、本部・美ら海、石垣、札幌、小樽、函館、旭川・富良野、帯広、ニセコ

「牧場に行く」のような場合は、オーナーが一番近いエリアを選ぶ想定。

### 4.5 行き先の候補の並び順（いつだけのとき）

エリアごとに、期間内のイベントの「おまけ度」を合計して並べる。

- 動員数のあるイベントは、規模の段階で点数（1万〜：1点、10万〜：2点、100万〜：3点）
- 見頃と展示もの：1点
- 同点ならイベントの件数が多い順、それでも同じならエリアの一覧の順

点数の細かい値は実装者が調整してよい。ただし、関数1つに閉じ込めて差し替えやすくする。

### 4.6 日程ずらしの提案

「両方（期間）」のとき、入れた期間の長さを変えずに、前後に最大3日ずらした候補を調べる。

- ずらすことで**新しく入る**イベント（今の期間には入らないもの）があれば提案する
- 提案は最大2件。新しく入るイベントの点数（4.5と同じ）が高い順。同点なら、ずらす日数が少ない順
- 文言の例：「3日前にずらすと（4/1〜4/5）、○○も見られます」＋「この日程で探す」（URLを更新）
- 新しく入るイベントがなければ何も出さない

### 4.7 混雑の警告（簡易版）

宿のデータは使わない。期間内のある日に、**動員100万人以上**のイベントが1つでもあれば、その日に「宿が埋まりやすい日」の印をつける。動員数は会期全体の合計の場合もあるので、厳密さは求めない。しきい値は設定の1か所で変えられるようにする。

### 4.8 そのほかのページ

- `/about/`：データについて（動員数は主催者発表の推計値であること、推定・平年値の意味、気象庁データの出典表記、問い合わせ先はGitHubのIssues）
- 404ページ
- `sitemap.xml`、`robots.txt`

## 5. データ

### 5.1 範囲

- 期間：2027年3月1日〜5月31日
- 地域：京都府、大阪府、沖縄県、北海道
- 種類：祭り、花火、グルメ・物産、ライトアップ、伝統行事、季節の見頃（桜）、期間限定の展示（teamLabの期間限定展示、美術館の特別展など）
- 規模：動員1万人以上。展示ものは会期が長く合計ではほぼ超えるので、動員数では絞らず人が選ぶ
- 件数の見込み：30〜50件

### 5.2 1イベント1ファイル（`data/events/<id>.yaml`）

`<id>` はURLにもなる英小文字とハイフンの名前（例：`kyoto-aoi-matsuri`）。年をまたいで同じイベントは同じID。

```yaml
id: kyoto-aoi-matsuri
name: 葵祭
kind: event            # event（祭り・花火など） | bloom（見頃） | exhibition（期間限定の展示）
genre: [伝統行事]        # 祭り / 花火 / グルメ・物産 / ライトアップ / 伝統行事 / 見頃 / 展示
country: JP            # 海外を足すときのため
region: domestic       # domestic | overseas
prefecture: 京都府
city: 京都市
lat: 35.0254
lng: 135.7621
nearest: { city: 京都市, airport: ITM }   # 宿や便へのディープリンク用
summary: 平安装束の行列が京都御所から下鴨神社・上賀茂神社へ進む。
official_url: https://...
attendance:            # kind: event のときだけ。なければ省略
  value: 30000
  basis: 主催者発表     # 主催者発表 / 報道 / 推計 など
  source_url: https://...
rules:                 # 例年ルール（配列）。推定の計算に使う。飛び飛びの日程は複数並べ、計算結果を合わせる
  - type: fixed        # fixed / nth_weekday / holiday_relative / manual
    month: 5
    day: 15
occurrences:           # 年ごとの日程
  - year: 2027
    status: estimated  # confirmed（公式発表） | estimated（例年ルールから計算） | normal（平年値）
    # dates はルールから計算できるときは省略してよい。confirmed と manual は必須
    dates:
      - { start: 2027-05-15, end: 2027-05-15 }   # 飛び飛びの日程は複数並べる
    source_url: https://...   # confirmed のときは必須
    note: 雨天順延あり
```

- `kind: event` では `attendance` を**必須**にする（1万人以上という線引きの根拠になるため）。公式の発表がないものは、オーナーが報道などから推計して `basis: 推計` とする。`bloom` と `exhibition` には持たせない（規模の絞り込み、点数の段階、混雑の警告の対象外）【設計者の判断】
- `kind: bloom` は、`rules` の代わりに気象庁の平年値を持ち、ビルド時に見頃の期間を計算する【設計者の判断】：

```yaml
bloom:
  station: 京都              # 気象台の名前
  flowering: 03-26          # 平年の開花日（MM-DD）
  full_bloom: 04-04         # 平年の満開日（MM-DD）
  forecast_url: https://tenki.jp/sakura/...   # 最新の開花予想へのリンク
```

- ビルド時にスキーマ（Astroのcontent collections＋zod）で検査し、項目の抜けや型の誤りはビルドを失敗させる
- `confirmed` に変えるときは、`dates` と `source_url` を必ず入れる

### 5.3 例年ルールと推定の計算（`src/lib/dates.ts`）

ビルド時に、ルールから対象年の日付を計算する。テストを先に書く（TDD）。

| type | 意味 | 例 |
| --- | --- | --- |
| `fixed` | 毎年同じ月日（複数日は `length`） | 葵祭 5/15 |
| `nth_weekday` | 第N○曜日。`n: -1` で最終 | 7月最終土曜 |
| `holiday_relative` | 祝日を基準に前後何日 | 海の日とその前日 |
| `manual` | 計算しない。旧暦など。`occurrences` に手で日付を入れる | 沖縄の旧暦の行事 |

- 複数日（`length`）と、ルールを複数組み合わせた飛び飛びの日程に対応する
- 祝日は2027年分が分かればよい。ライブラリを使うか、2027年の祝日の一覧をコードに持つかは実装者が決める
- `occurrences` に `dates` があればそれを優先し、なければルールから計算する

### 5.4 桜の見頃（`kind: bloom`）

- 気象庁の**平年の開花日・満開日**を使い、`status: normal`（平年値）として持つ。表示は「見頃は例年3/28〜4/7ごろ（平年値）」
- 見頃の期間は「開花日〜満開日の1週間後」とする（実装者が調整してよい）
- 最新の開花予想（tenki.jpなど）へのリンクを置く。民間の予想は取り込まない
- 1エリアに1件（例：京都の桜、大阪の桜、札幌の桜、函館の桜）。観測地点はエリアに最も近い気象台
- 沖縄の桜（ヒカンザクラ）は1〜2月で期間外なので、MVPでは入れない
- `/about/` と見頃のページに、出典（気象庁）を表記する。政府標準利用規約に従う

### 5.5 データの集め方

**実装計画とは別の作業にする**【設計者の判断】。実装計画には、テストと画面の確認に使う見本のデータ（5件ほど、`kind` 3種類をすべて含む）と、`draft-events`・`verify-events` のスキル（5.6）だけを入れる。本番の30〜50件は、地域ごと（京都・大阪・沖縄・北海道）に1つずつPRを作る。MVPの完成の判定は「実装の完了」と「4地域のデータのマージ」の両方。

**原則：オーナーは調べない、書かない。** 調査・記述・照合はClaude Codeとサブエージェントが行い、オーナーは「OK／NG」を選ぶだけにする。

1. **下書き**：Claude Codeが、公式サイト・観光協会・気象庁のページを調べて下書きのYAMLを作る（すべての値に出典のURL）
2. **照合**：下書きを書いたのとは**別のサブエージェント**が、出典のページだけを見て、日程・場所・動員数を1件ずつ照合する。下書きと照合が食い違った箇所、出典が見つからない箇所、推計した箇所には印をつける
3. **PR**：ブランチを切ってPRを作る。PRの説明には、印のついた箇所だけを選択肢つきで並べる（例：「動員数：A. 報道の3万人を使う　B. 入れない（このイベントを外す）」）。印のない箇所は照合済みとして、オーナーは見なくてよい
4. **オーナー**：印のついた箇所の選択肢を選び、マージする。調べ直しや書き直しはしない
5. **確定への切り替え**：毎月、Claude Codeが推定のイベントの公式サイトを調べ直し、発表があったものを `confirmed` に変えるPRを作る（同じく照合つき）
6. **展示もの**：Claude Codeが候補を理由つきで並べ、オーナーは入れるものに印をつけるだけ

照合をしても、出典のページ自体の誤りや古さまでは防げない。そのため、確定の日程も出典のリンクを必ず表示し、使う人が最後に確かめられるようにする。

### 5.6 繰り返す作業はスキルにする

同じ手順を毎回正しく繰り返すため、プロジェクトのスキル（`.claude/skills/`）として手順を書き、サブエージェントに実行させる。スキルは superpowers:writing-skills に沿って作り、実際の数件で試してから使う。

| スキル | いつ作るか | 中身 |
| --- | --- | --- |
| `draft-events` | MVP | 地域と期間を受け取り、候補を調べて下書きのYAMLを作る。線引き（5.1）、スキーマ（5.2）、出典の付け方を守る |
| `verify-events` | MVP | 下書きを出典だけで照合し、印のついた箇所を選択肢つきで返す。下書きを作ったのとは別のサブエージェントで動かす |
| `refresh-dates` | MVP（運用） | 推定のイベントの日程の発表を調べ直し、確定に変えるPRを作る。毎月1回 |
| `check-image-license` | 海外を足すとき | 写真の候補をWikimedia CommonsのAPI（`imageinfo` の `extmetadata`）で調べ、ライセンス・作者・帰属表示の要否を取り出す。使ってよいのはCC0、パブリックドメイン、CC BY、CC BY-SAだけ（NC・ND・不明は除外）。帰属表示の文をYAMLに書き込む。判断に迷うものだけオーナーに選択肢で出す |

- 繰り返しの実行（`refresh-dates` の毎月など）は、慣れてきたら定期実行にする候補
- 件数が増えて重くなったら、照合の一部をローカルLLMか安いAPIに移す

- ビルド時に、全イベントの日付を計算済みにしたJSON（`/data/events.json`）を出力し、トップはそれを読み込んで検索する。数十件なので1ファイルでよい

- ブラウザで動く部分（フォームと結果）の書き方（AstroのIslandで小さなUIライブラリを使うか、素のTypeScriptか）は実装者が決める。JSは小さく保つ

## 7. 公開と運用

- Cloudflare：GitHubのリポジトリとつなぎ、mainへのプッシュで本番、PRごとにプレビューURL。MVPは `himekuri-tabi.idotworks-lab.workers.dev`
- **.comへの切り替えの準備**（MVPから入れておく）：
  - サイトのURLは設定の1か所（Astroの `site`。環境変数で上書きできる）にだけ書く。canonical、OGPの `og:url`・`og:image`、`sitemap.xml`、`robots.txt` は、すべてそこから組み立てる。コードやデータにホスト名を直接書かない
  - ページ内のリンクは相対パスにする
  - 切り替えの手順を `docs/` に書いておく：ドメインを取る → Cloudflareでカスタムドメインを設定する → `site` を変える → `workers.dev` から新しいドメインへ301で転送する → Search Consoleに登録する
- アクセス解析：Cloudflare Web Analytics（Cookieなし、無料）。Workersでは自動で入らないので、解析のトークン（公開してよい値）を `src/config.ts` の `CF_BEACON_TOKEN` に書く
- Search Console：**.comに切り替えてから登録する**。`workers.dev` の間は登録しない（移転の手間を避けるため）。`sitemap.xml` は最初から生成しておく
- 宿のリンク：楽天トラベルのアフィリエイト（無料）。エリアと日付を載せた検索のリンクにする。アカウントができるまでは、アフィリエイトのIDなしの普通のリンクにしておき、IDを設定1か所で差し込めるようにする
- CI：PRごとに型チェック、テスト、ビルド（スキーマ検査を含む）を通す（GitHub Actionsの無料枠）

## 8. テスト

- `dates.ts`、`search.ts`、`score.ts`、`shift.ts`、`geo.ts` はユニットテストを先に書く
  - 例：2027年7月の最終土曜は7/31。葵祭（固定5/15）。海の日の前日。飛び飛びの日程。月の境目をまたぐ期間
